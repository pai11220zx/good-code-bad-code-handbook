## 01. Package and file organization

> Keep packages small, cohesive, and named by what callers need instead of by internal technical layers.

**Tags:** `packages` `organization` `boundaries` · [View on site](https://good-code-bad-code.pages.dev/tracks/go/package-and-file-organization)

### ✅ Good Code — `reviews/service.go`

```go
package reviews

type Service struct {
    repo Repository
}

// Constructor injection makes the dependency visible.
func NewService(repo Repository) *Service {
    return &Service{repo: repo}
}

func (s *Service) Publish(ctx context.Context, id string) error {
    review, err := s.repo.Find(ctx, id)
    if err != nil {
        return err
    }

    review.Publish()
    return s.repo.Save(ctx, review)
}
```

### ❌ Bad Code — `utils/review_helpers.go`

```go
package utils

// A global database hides what callers depend on.
var ReviewDB *sql.DB

func PublishReview(id string) error {
    row := ReviewDB.QueryRow("select title from reviews where id = ?", id)
    var title string
    if err := row.Scan(&title); err != nil {
        return err
    }

    _, err := ReviewDB.Exec("update reviews set status = 'published' where id = ?", id)
    return err
}
```

### 🔍 What to review

- **Good Code:** The good version gives the package a domain name, keeps dependencies explicit, and exports a small service boundary.
- **Bad Code:** The bad version hides review behavior in a generic `utils` package with global database state. Callers cannot tell what the package owns.

### 📝 Review notes

In Go, package names show up at every call site. Prefer names that let callers read code naturally and avoid packages that become catch-all drawers for unrelated helpers.

### 💡 Takeaway

> **A Go package is an API boundary; review whether its name and exported surface make that boundary clear.**

## 02. Naming and exported APIs

> Export only the names callers need and avoid repeating the package name inside exported identifiers.

**Tags:** `naming` `api` `exports` · [View on site](https://good-code-bad-code.pages.dev/tracks/go/naming-and-exported-api)

### ✅ Good Code — `reviews/repository.go`

```go
package reviews

// Callers see this as reviews.Repository.
type Repository interface {
    Find(ctx context.Context, id string) (Review, error)
    Save(ctx context.Context, review Review) error
}

type Review struct {
    ID     string
    Title  string
    Status Status
}

type Status string
```

### ❌ Bad Code — `reviews/repository.go`

```go
package reviews

// The exported name repeats words the package already says.
type ReviewsRepositoryInterface interface {
    GetReviewObjectFromReviewID(ctx context.Context, reviewID string) (ReviewObject, error)
    SaveReviewObjectToDatabase(ctx context.Context, reviewObject ReviewObject) error
}

type ReviewObject struct {
    ReviewID     string
    ReviewTitle  string
    ReviewStatus string
}
```

### 🔍 What to review

- **Good Code:** The good version uses the package name to provide context, so callers read `reviews.Repository`, `reviews.Review`, and `reviews.Status`.
- **Bad Code:** The bad version repeats "review" and implementation detail in every exported name. The API gets noisy and harder to change.

### 📝 Review notes

When reviewing Go APIs, read the code from the caller side. If the call site sounds redundant, the exported name is probably carrying words the package name already provides.

### 💡 Takeaway

> **Exported names are part of the package contract, so they should be minimal, clear, and caller-oriented.**

## 03. Error handling and wrapping

> Return errors with useful context and wrap underlying errors when callers should be able to inspect them.

**Tags:** `errors` `wrapping` `sentinels` · [View on site](https://good-code-bad-code.pages.dev/tracks/go/error-handling-wrapping)

### ✅ Good Code — `reviews/repository.go`

```go
// Sentinel error lets callers check the not-found case.
var ErrReviewNotFound = errors.New("review not found")

func (r *Repository) Find(ctx context.Context, id string) (Review, error) {
    review, err := r.store.FindReview(ctx, id)
    if errors.Is(err, store.ErrNotFound) {
        // %w preserves an error chain for errors.Is/errors.As.
        return Review{}, fmt.Errorf("find review %s: %w", id, ErrReviewNotFound)
    }
    if err != nil {
        return Review{}, fmt.Errorf("find review %s: %w", id, err)
    }

    return review, nil
}
```

### ❌ Bad Code — `reviews/repository.go`

```go
func (r *Repository) Find(ctx context.Context, id string) (Review, error) {
    review, err := r.store.FindReview(ctx, id)
    if err != nil {
        log.Println("find review failed", err)
        // The original reason is lost behind a vague error.
        return Review{}, errors.New("failed")
    }

    return review, nil
}
```

### 🔍 What to review

- **Good Code:** The good version adds operation context and preserves an inspectable error chain for callers that use `errors.Is`.
- **Bad Code:** The bad version logs and replaces the original error with a vague message. Callers lose the reason and cannot make a precise decision.

### 📝 Review notes

Do not wrap every error blindly. Wrap when exposing the underlying error is part of the contract; otherwise add a clear message without leaking internal details.

### 💡 Takeaway

> **Errors are values in Go; review both the message for humans and the wrapping contract for callers.**

## 04. Context cancellation

> Accept context at API boundaries and pass it through I/O so cancellation, deadlines, and request scope are honored.

**Tags:** `context` `cancellation` `io` · [View on site](https://good-code-bad-code.pages.dev/tracks/go/context-cancellation)

### ✅ Good Code — `reviews/client.go`

```go
func (c *Client) FetchReview(ctx context.Context, id string) (Review, error) {
    // Tie the outbound request to the caller's timeout/cancel signal.
    req, err := http.NewRequestWithContext(
        ctx,
        http.MethodGet,
        c.baseURL+"/reviews/"+id,
        nil,
    )
    if err != nil {
        return Review{}, err
    }

    resp, err := c.http.Do(req)
    if err != nil {
        return Review{}, err
    }
    defer resp.Body.Close()

    var review Review
    if err := json.NewDecoder(resp.Body).Decode(&review); err != nil {
        return Review{}, err
    }
    return review, nil
}
```

### ❌ Bad Code — `reviews/client.go`

```go
func (c *Client) FetchReview(id string) (Review, error) {
    // http.Get has no caller-controlled lifetime.
    resp, err := http.Get(c.baseURL + "/reviews/" + id)
    if err != nil {
        return Review{}, err
    }
    defer resp.Body.Close()

    var review Review
    if err := json.NewDecoder(resp.Body).Decode(&review); err != nil {
        return Review{}, err
    }
    return review, nil
}
```

### 🔍 What to review

- **Good Code:** The good version accepts a context and attaches it to the outbound HTTP request, so cancellation and deadlines can stop the whole operation.
- **Bad Code:** The bad version creates a request with no caller-controlled lifetime. If the caller times out or disconnects, the work can keep running.

### 📝 Review notes

Context is not a bag for optional parameters. In review, look for database calls, HTTP calls, locks, and goroutines that should stop when the caller stops caring.

### 💡 Takeaway

> **Context belongs on work that can block, wait, or leave the process.**

## 05. Interfaces at boundaries

> Define small interfaces where behavior is consumed instead of forcing every producer to satisfy a large package-wide contract.

**Tags:** `interfaces` `dependencies` `testing` · [View on site](https://good-code-bad-code.pages.dev/tracks/go/interfaces-at-boundaries)

### ✅ Good Code — `reviews/notifier.go`

```go
// The service only needs one behavior: send email.
type Mailer interface {
    Send(ctx context.Context, message Message) error
}

type Service struct {
    mailer Mailer
}

func (s *Service) RequestReview(ctx context.Context, review Review) error {
    return s.mailer.Send(ctx, Message{
        To:      review.ReviewerEmail,
        Subject: "Review requested",
    })
}
```

### ❌ Bad Code — `notifications/client.go`

```go
// This forces email callers to depend on unrelated behavior.
type NotificationClient interface {
    SendEmail(ctx context.Context, to string, subject string, body string) error
    SendSMS(ctx context.Context, phone string, body string) error
    SendSlack(ctx context.Context, channel string, body string) error
    Close() error
}

func RequestReview(ctx context.Context, client NotificationClient, review Review) error {
    return client.SendEmail(ctx, review.ReviewerEmail, "Review requested", "")
}
```

### 🔍 What to review

- **Good Code:** The good version names the one behavior the service needs, so production clients and tests can provide the smallest useful implementation.
- **Bad Code:** The bad version makes a caller depend on email, SMS, Slack, and lifecycle methods even though it only sends one email.

### 📝 Review notes

Small interfaces keep package boundaries flexible. If a function only calls one method, requiring a four-method interface is usually a coupling smell.

### 💡 Takeaway

> **In Go, interfaces are most useful when they describe what the caller needs right now.**

## 06. Struct validation and zero values

> Design structs so zero values are either useful or validated before the value crosses an important boundary.

**Tags:** `structs` `validation` `zero values` · [View on site](https://good-code-bad-code.pages.dev/tracks/go/struct-validation-zero-values)

### ✅ Good Code — `reviews/review.go`

```go
type Review struct {
    ID    string
    Title string
    Body  string
}

// Constructor validates the fields that cannot be empty.
func NewReview(id string, title string, body string) (Review, error) {
    title = strings.TrimSpace(title)
    if id == "" {
        return Review{}, errors.New("id is required")
    }
    if title == "" {
        return Review{}, errors.New("title is required")
    }

    return Review{ID: id, Title: title, Body: body}, nil
}
```

### ❌ Bad Code — `reviews/review.go`

```go
type Review struct {
    ID    string
    Title string
    Body  string
}

// Empty ID and title can become a "valid" Review.
func CreateReview(id string, title string, body string) Review {
    return Review{
        ID:    id,
        Title: title,
        Body:  body,
    }
}
```

### 🔍 What to review

- **Good Code:** The good version makes invalid construction visible and returns a useful error before the value enters the rest of the system.
- **Bad Code:** The bad version allows empty IDs and titles to move through the codebase as if they were valid reviews.

### 📝 Review notes

Go's zero values are useful for many infrastructure types. For domain types, review whether zero values are valid, and if not, where validation is enforced.

### 💡 Takeaway

> **A zero value can be a feature, but domain objects still need clear validity rules.**

## 07. Goroutines and channel ownership

> Make goroutine lifetime and channel closing ownership explicit so concurrent code can stop cleanly.

**Tags:** `goroutines` `channels` `concurrency` · [View on site](https://good-code-bad-code.pages.dev/tracks/go/goroutines-and-channel-ownership)

### ✅ Good Code — `reviews/worker.go`

```go
func StartWorker(ctx context.Context, jobs <-chan Job, results chan<- Result) {
    go func() {
        // The sending goroutine owns closing the output channel.
        defer close(results)

        for {
            select {
            case <-ctx.Done():
                // Context cancellation gives the goroutine a clean stop.
                return
            case job, ok := <-jobs:
                if !ok {
                    return
                }
                results <- process(job)
            }
        }
    }()
}
```

### ❌ Bad Code — `reviews/worker.go`

```go
func StartWorker(jobs chan Job, results chan Result) {
    go func() {
        // No cancel path means this goroutine depends on jobs closing.
        for job := range jobs {
            results <- process(job)
        }
    }()
}

func StopWorker(results chan Result) {
    // Closing a channel from the outside can race with senders.
    close(results)
}
```

### 🔍 What to review

- **Good Code:** The good version shows who reads, who writes, who closes the output channel, and how the goroutine exits when the context is canceled.
- **Bad Code:** The bad version leaves lifetime implicit and lets a separate function close a channel it does not own.

### 📝 Review notes

In Go concurrency review, ask: who starts this goroutine, who stops it, who closes each channel, and what happens if the receiver leaves early?

### 💡 Takeaway

> **The code that starts a goroutine should make its stop condition and channel ownership visible.**

## 08. Defer and resource cleanup

> Use defer close to make cleanup follow resource acquisition and cover every return path.

**Tags:** `defer` `cleanup` `resources` · [View on site](https://good-code-bad-code.pages.dev/tracks/go/defer-resource-cleanup)

### ✅ Good Code — `reviews/importer.go`

```go
func ImportReviews(path string) error {
    file, err := os.Open(path)
    if err != nil {
        return err
    }
    // Put cleanup next to the successful open.
    defer file.Close()

    scanner := bufio.NewScanner(file)
    for scanner.Scan() {
        if err := importLine(scanner.Text()); err != nil {
            return err
        }
    }

    return scanner.Err()
}
```

### ❌ Bad Code — `reviews/importer.go`

```go
func ImportReviews(path string) error {
    file, err := os.Open(path)
    if err != nil {
        return err
    }

    scanner := bufio.NewScanner(file)
    for scanner.Scan() {
        if err := importLine(scanner.Text()); err != nil {
            return err
        }
    }

    // Early returns above skip this cleanup.
    file.Close()
    return scanner.Err()
}
```

### 🔍 What to review

- **Good Code:** The good version defers cleanup immediately after opening the file, so early returns still release the resource.
- **Bad Code:** The bad version closes only on the happy path. If importing a line fails, the file handle leaks until the process cleans it up.

### 📝 Review notes

`defer` is strongest when it sits right after successful acquisition. Review code paths with early returns and make sure cleanup does not depend on reaching the bottom of the function.

### 💡 Takeaway

> **Cleanup should sit close to acquisition so reviewers can see every path releases the resource.**

## 09. Table-driven tests

> Use table-driven tests to make related cases explicit while keeping each case named and independently diagnosable.

**Tags:** `testing` `table-driven` `coverage` · [View on site](https://good-code-bad-code.pages.dev/tracks/go/table-driven-tests)

### ✅ Good Code — `reviews/slug_test.go`

```go
func TestSlugify(t *testing.T) {
    // Each row names one variation of the same behavior.
    tests := []struct {
        name string
        in   string
        want string
    }{
        {name: "lowercases title", in: "Code Review", want: "code-review"},
        {name: "trims spaces", in: "  Draft Notes  ", want: "draft-notes"},
    }

    for _, tt := range tests {
        // Subtests make failures point to the exact case.
        t.Run(tt.name, func(t *testing.T) {
            got := Slugify(tt.in)
            if got != tt.want {
                t.Fatalf("Slugify(%q) = %q, want %q", tt.in, got, tt.want)
            }
        })
    }
}
```

### ❌ Bad Code — `reviews/slug_test.go`

```go
func TestSlugify(t *testing.T) {
    // Repeated assertions give vague failures.
    if Slugify("Code Review") != "code-review" {
        t.Fatal("bad slug")
    }

    if Slugify("  Draft Notes  ") != "draft-notes" {
        t.Fatal("bad slug")
    }
}
```

### 🔍 What to review

- **Good Code:** The good version names each case, uses subtests, and includes enough failure output to understand the broken input and expected value.
- **Bad Code:** The bad version repeats assertions with vague messages. When it fails, the reviewer has to reverse engineer the case.

### 📝 Review notes

Table-driven tests work best when cases are genuinely variations of one behavior. If the setup or assertion shape changes per row, split the tests instead.

### 💡 Takeaway

> **A test table should improve coverage and readability, not hide which case failed.**

## 10. JSON HTTP handler boundaries

> Keep HTTP handlers focused on method checks, JSON decoding, validation, service calls, and response shape.

**Tags:** `http` `json` `handlers` · [View on site](https://good-code-bad-code.pages.dev/tracks/go/json-http-handler-boundaries)

### ✅ Good Code — `reviews/handler.go`

```go
type createReviewRequest struct {
    Title string
    Body  string
}

func (h *Handler) CreateReview(w http.ResponseWriter, r *http.Request) {
    if r.Method != http.MethodPost {
        http.Error(w, "method not allowed", http.StatusMethodNotAllowed)
        return
    }
    defer r.Body.Close()

    var input createReviewRequest
    decoder := json.NewDecoder(r.Body)
    // Reject unknown JSON fields instead of silently accepting typos.
    decoder.DisallowUnknownFields()
    if err := decoder.Decode(&input); err != nil {
        http.Error(w, "invalid json", http.StatusBadRequest)
        return
    }

    // Pass the request context so cancellation reaches the service.
    review, err := h.service.Create(r.Context(), input.Title, input.Body)
    if err != nil {
        http.Error(w, "create review failed", http.StatusInternalServerError)
        return
    }

    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(http.StatusCreated)
    json.NewEncoder(w).Encode(review)
}
```

### ❌ Bad Code — `reviews/handler.go`

```go
func (h *Handler) CreateReview(w http.ResponseWriter, r *http.Request) {
    // Ignored read/decode errors turn bad input into normal data.
    body, _ := io.ReadAll(r.Body)
    var data map[string]string
    json.Unmarshal(body, &data)

    review, _ := h.service.Create(
        // Background context loses timeout and disconnect signals.
        context.Background(),
        data["title"],
        data["body"],
    )

    json.NewEncoder(w).Encode(review)
}
```

### 🔍 What to review

- **Good Code:** The good version checks the method, closes the body, decodes into a request type, rejects unknown fields, passes `r.Context()`, and sets a clear response status.
- **Bad Code:** The bad version ignores decoding errors, uses a loose map, loses request cancellation, and always writes a success-looking response.

### 📝 Review notes

HTTP handlers are edge code. Review them for method gates, request size and decoding behavior, validation, context propagation, service boundaries, and response status consistency.

### 💡 Takeaway

> **A Go HTTP handler should make request parsing and response writing explicit at the edge.**
