## 01. Pointer ownership at boundaries

> Make write ownership visible by receiving caller-owned buffers with size, instead of returning hidden shared storage.

**Tags:** `pointers` `ownership` `buffers` · [View on site](https://good-code-bad-code.pages.dev/tracks/c/pointer-ownership)

### ✅ Good Code — `src/review_title.c`

```c
#include <stddef.h>
#include <string.h>

int copy_review_title(char *dst, size_t dst_size, const char *src)
{
    // Caller-owned storage makes the write target visible.
    if (dst == NULL || src == NULL || dst_size == 0) {
        return -1;
    }

    size_t length = 0;
    while (length < dst_size && src[length] != '\0') {
        length++;
    }

    if (length == dst_size) {
        return -1;
    }

    memcpy(dst, src, length + 1);
    return 0;
}
```

### ❌ Bad Code — `review_title.c`

```c
#include <string.h>

char *copy_review_title(char *src)
{
    // Returning shared static storage hides ownership across callers.
    static char title[64];
    strcpy(title, src);
    return title;
}
```

### 🔍 What to review

- **Good Code:** The good version asks the caller to supply the destination buffer and its size. Reviewers can see where the write lands, how overflow is rejected, and how the error path returns.
- **Bad Code:** The bad version returns a pointer to one shared static buffer. Two callers can overwrite each other, and the unchecked `strcpy` can write past the fixed array.

### 📝 Review notes

In C reviews, start pointer questions at the function boundary. For every pointer, ask whether the function reads it, writes it, takes ownership, or only borrows it for the call.

### 💡 Takeaway

> **A C function that writes through a pointer should say who owns the storage and how large that storage is.**

## 02. Buffer bounds and formatted output

> Use bounded formatting APIs and check their return values before treating a fixed buffer as complete.

**Tags:** `buffers` `bounds` `formatting` · [View on site](https://good-code-bad-code.pages.dev/tracks/c/buffer-bounds)

### ✅ Good Code — `src/review_label.c`

```c
#include <stddef.h>
#include <stdio.h>

int format_review_label(char *dst, size_t dst_size, int id)
{
    // snprintf reports when the label does not fit.
    int written = snprintf(dst, dst_size, "review-%d", id);
    if (written < 0 || (size_t) written >= dst_size) {
        return -1;
    }

    return 0;
}
```

### ❌ Bad Code — `review_label.c`

```c
#include <stdio.h>

void format_review_label(char *dst, int id)
{
    // sprintf cannot see the destination size.
    sprintf(dst, "review-%d", id);
}
```

### 🔍 What to review

- **Good Code:** The good version uses `snprintf`, passes the buffer size, and treats truncation as a failure. The caller receives a result code instead of a silently shortened label.
- **Bad Code:** The bad version uses `sprintf`, so the function cannot prove the destination is large enough. A longer id can overwrite adjacent memory.

### 📝 Review notes

For fixed buffers, review both the API and the return value. A bounded function prevents many overwrites, but the code still has to decide whether truncated data is allowed.

### 💡 Takeaway

> **A bounded write still needs a return-value check, because truncation can be a data bug rather than a safe result.**

## 03. Allocation and free ownership

> Pair heap allocation with a visible free function so callers know when they own memory and when to release it.

**Tags:** `malloc` `free` `ownership` · [View on site](https://good-code-bad-code.pages.dev/tracks/c/allocation-free-ownership)

### ✅ Good Code — `src/review.c`

```c
#include <stdlib.h>
#include <string.h>

struct Review {
    char *title;
};

struct Review *review_create(const char *title)
{
    struct Review *review = malloc(sizeof *review);
    if (review == NULL) {
        return NULL;
    }

    size_t length = strlen(title) + 1;
    review->title = malloc(length);
    if (review->title == NULL) {
        free(review);
        return NULL;
    }

    // The create/free pair states who owns heap memory.
    memcpy(review->title, title, length);
    return review;
}

void review_free(struct Review *review)
{
    if (review != NULL) {
        free(review->title);
        free(review);
    }
}
```

### ❌ Bad Code — `review.c`

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

char *review_title_for_display(const char *title)
{
    // Heap allocation without a matching owner leaks per call.
    char *label = malloc(strlen(title) + 10);
    sprintf(label, "Review: %s", title);
    return label;
}
```

### 🔍 What to review

- **Good Code:** The good version exposes a constructor and a matching `review_free`. If title allocation fails, it releases the struct before returning failure.
- **Bad Code:** The bad version allocates a display label and returns it without naming who must free it. Call sites can leak memory or free the same pointer in inconsistent places.

### 📝 Review notes

When reviewing `malloc`, search for the matching `free` contract, not only a nearby `free` call. A named release function makes ownership easier to test and document.

### 💡 Takeaway

> **Heap ownership should appear as a contract: the code that creates memory must name the code that releases it.**

## 04. Const correctness for read paths

> Mark read-only pointers as const so callers and reviewers know a check will not mutate shared state.

**Tags:** `const` `pointers` `contracts` · [View on site](https://good-code-bad-code.pages.dev/tracks/c/const-correctness)

### ✅ Good Code — `src/review_score.c`

```c
#include <stdbool.h>

struct Review {
    int score;
};

bool review_score_is_passing(const struct Review *review)
{
    // const promises this check will not mutate the review.
    if (review == NULL) {
        return false;
    }

    return review->score >= 70;
}
```

### ❌ Bad Code — `review_score.c`

```c
#include <stdbool.h>

struct Review {
    int score;
};

bool review_score_is_passing(struct Review *review)
{
    // A read check that rewrites state surprises callers.
    if (review->score < 0) {
        review->score = 0;
    }

    return review->score >= 70;
}
```

### 🔍 What to review

- **Good Code:** The good version accepts a `const struct Review *`, so the compiler helps enforce that the score check is read-only.
- **Bad Code:** The bad version receives a mutable pointer and normalizes negative scores during a predicate call. A caller asking a question gets state mutation as a hidden side effect.

### 📝 Review notes

In C, `const` is one of the cheapest review signals. If a function reads data only, ask for `const`; if it cannot be `const`, the mutation should be named in the function.

### 💡 Takeaway

> **Const is part of the API contract in C; it separates read-only review paths from functions that may change data.**

## 05. Struct ownership and borrowed views

> Use small view structs to state borrowed data and lengths, instead of returning pointers to temporary storage.

**Tags:** `structs` `ownership` `views` · [View on site](https://good-code-bad-code.pages.dev/tracks/c/struct-ownership)

### ✅ Good Code — `src/review_view.c`

```c
#include <stddef.h>
#include <string.h>

struct ReviewView {
    const char *title;
    size_t title_len;
};

struct ReviewView review_view_from_title(const char *title)
{
    // A view stores borrowed data plus its length.
    return (struct ReviewView) {
        .title = title,
        .title_len = strlen(title),
    };
}
```

### ❌ Bad Code — `review_view.c`

```c
#include <string.h>

struct ReviewView {
    char *title;
};

struct ReviewView default_review_view(void)
{
    char title[32];
    strcpy(title, "Draft review");

    // Returning stack storage breaks after the function returns.
    return (struct ReviewView) { .title = title };
}
```

### 🔍 What to review

- **Good Code:** The good version returns a borrowed view: it keeps the caller-owned pointer and records the length. The `const` field tells readers that the view will not edit the title.
- **Bad Code:** The bad version stores a pointer to a local stack array. The pointer becomes invalid as soon as the function returns, so later reads have undefined behavior.

### 📝 Review notes

For structs with pointer fields, ask whether the struct owns the memory or only borrows it. Borrowed views should be short-lived, const where possible, and paired with sizes.

### 💡 Takeaway

> **A struct that borrows memory should say so through const pointers and lengths, while stack storage must never escape its function.**

## 06. Error codes that name failures

> Return named error codes when validation can fail for multiple reasons, so callers can branch without guessing.

**Tags:** `errors` `validation` `contracts` · [View on site](https://good-code-bad-code.pages.dev/tracks/c/error-codes)

### ✅ Good Code — `src/review_validation.c`

```c
enum ReviewStatus {
    REVIEW_OK = 0,
    REVIEW_EMPTY_TITLE = -1,
    REVIEW_SCORE_OUT_OF_RANGE = -2,
};

enum ReviewStatus validate_review(const char *title, int score)
{
    // Named result codes tell callers which input failed.
    if (title == 0 || title[0] == '\0') {
        return REVIEW_EMPTY_TITLE;
    }
    if (score < 0 || score > 100) {
        return REVIEW_SCORE_OUT_OF_RANGE;
    }

    return REVIEW_OK;
}
```

### ❌ Bad Code — `review_validation.c`

```c
int validate_review(const char *title, int score)
{
    // A single -1 erases which validation failed.
    if (title == 0 || title[0] == '\0') {
        return -1;
    }
    if (score < 0 || score > 100) {
        return -1;
    }

    return 0;
}
```

### 🔍 What to review

- **Good Code:** The good version gives each failure a named enum value. Callers can log a useful reason, map it to a response, or assert it in tests.
- **Bad Code:** The bad version returns `-1` for every validation failure. Callers must repeat validation logic or show a generic error to the user.

### 📝 Review notes

When a function can fail, ask what the caller needs next. If the caller only needs success or failure, a boolean may fit. If it needs a reason, name the reason in the return type.

### 💡 Takeaway

> **A C error code is useful when it preserves the reason a caller needs for logging, retrying, or showing a message.**

## 07. File I/O cleanup paths

> Keep cleanup on every file I/O path so early returns and write failures do not leak file handles.

**Tags:** `files` `cleanup` `resources` · [View on site](https://good-code-bad-code.pages.dev/tracks/c/file-io-cleanup)

### ✅ Good Code — `src/review_file.c`

```c
#include <stdio.h>

int save_review(const char *path, const char *body)
{
    FILE *file = fopen(path, "w");
    if (file == NULL) {
        return -1;
    }

    // One cleanup exit closes the file on every failure path.
    int result = 0;
    if (fputs(body, file) == EOF) {
        result = -1;
    }
    if (fclose(file) == EOF) {
        result = -1;
    }

    return result;
}
```

### ❌ Bad Code — `review_file.c`

```c
#include <stdio.h>

int save_review(const char *path, const char *body)
{
    FILE *file = fopen(path, "w");
    if (file == NULL) {
        return -1;
    }

    if (fputs(body, file) == EOF) {
        // This early return leaves the file handle open.
        return -1;
    }

    fclose(file);
    return 0;
}
```

### 🔍 What to review

- **Good Code:** The good version keeps close logic on the same path as the write result. Both `fputs` and `fclose` can affect the final status.
- **Bad Code:** The bad version returns before `fclose` when the write fails. That leaks the file handle and can also hide buffered write errors.

### 📝 Review notes

With C file I/O, review every return after `fopen`. A cleanup label or one exit path often makes the release path easier to audit than many early returns.

### 💡 Takeaway

> **File cleanup should be visible on success and failure paths, especially when the function can return before the bottom.**

## 08. Integer overflow before allocation

> Check multiplication before allocating arrays so a wrapped byte count does not create a too-small buffer.

**Tags:** `integers` `overflow` `malloc` · [View on site](https://good-code-bad-code.pages.dev/tracks/c/integer-overflow)

### ✅ Good Code — `src/review_scores.c`

```c
#include <stdint.h>
#include <stdlib.h>

int allocate_scores(size_t count, int **out)
{
    // Check multiplication before asking malloc for bytes.
    if (out == NULL || count > SIZE_MAX / sizeof **out) {
        return -1;
    }

    *out = malloc(count * sizeof **out);
    return *out == NULL ? -1 : 0;
}
```

### ❌ Bad Code — `review_scores.c`

```c
#include <stdlib.h>

int *allocate_scores(size_t count)
{
    // Overflow can make malloc reserve fewer bytes than requested.
    return malloc(count * sizeof(int));
}
```

### 🔍 What to review

- **Good Code:** The good version checks that `count * sizeof **out` fits in `size_t` before allocating. The output pointer is written only after the size is proven.
- **Bad Code:** The bad version multiplies directly inside `malloc`. If the multiplication wraps, the loop that fills the array can write past the smaller allocation.

### 📝 Review notes

Review allocation size math before the allocation call. The larger the count comes from user input, files, or network data, the more important the overflow check becomes.

### 💡 Takeaway

> **Allocation math must be checked before `malloc`, because overflow can turn a large request into a small allocation.**

## 09. Compiler warning contracts

> Make compiler assumptions visible in source so warning flags and language version mistakes fail during review or CI.

**Tags:** `compiler` `warnings` `builds` · [View on site](https://good-code-bad-code.pages.dev/tracks/c/compiler-warnings-flags)

### ✅ Good Code — `src/review_parse.c`

```c
#include <stdlib.h>

#if !defined(__STDC_VERSION__) || __STDC_VERSION__ < 201112L
#error "compile with C11 or newer"
#endif

int parse_review_score(const char *value)
{
    // Source-level build contracts keep compiler assumptions visible.
    if (value == NULL) {
        return -1;
    }

    return atoi(value);
}
```

### ❌ Bad Code — `review_parse.c`

```c
#include <stdlib.h>

int parse_review_score(char *value)
{
    // Missing build contracts let warnings stay optional.
    return atoi(value);
}
```

### 🔍 What to review

- **Good Code:** The good version states the required C version and uses `const` on the input pointer. CI can compile with strict flags and fail when the contract is not met.
- **Bad Code:** The bad version leaves build assumptions outside the code. A project can compile it with weak flags and miss nullability, const, or standard-version problems.

### 📝 Review notes

Compiler flags are part of code quality in C. Review the source and the build command together, especially for `-Wall`, `-Wextra`, `-Werror`, and the selected C standard.

### 💡 Takeaway

> **Build assumptions belong near the code they protect, because reviewers cannot infer warning policy from a function body alone.**

## 10. Unit tests with boundary cases

> Write small C tests that assert boundary behavior directly, instead of printing output for a human to inspect.

**Tags:** `tests` `assertions` `boundaries` · [View on site](https://good-code-bad-code.pages.dev/tracks/c/unit-tests-cases)

### ✅ Good Code — `tests/review_label_test.c`

```c
#include <assert.h>
#include <string.h>

static void test_review_label_fits_buffer(void)
{
    char buffer[16];

    // Test data names the boundary condition under review.
    assert(format_review_label(buffer, sizeof buffer, 42) == 0);
    assert(strcmp(buffer, "review-42") == 0);
}

int main(void)
{
    test_review_label_fits_buffer();
    return 0;
}
```

### ❌ Bad Code — `tests/review_label_test.c`

```c
#include <stdio.h>

int main(void)
{
    char buffer[16];
    format_review_label(buffer, sizeof buffer, 42);

    // Printing output asks humans to judge the test result.
    printf("%s\n", buffer);
    return 0;
}
```

### 🔍 What to review

- **Good Code:** The good version turns the expected label into assertions. The test fails automatically when the formatter returns an error or writes the wrong text.
- **Bad Code:** The bad version prints the result and exits successfully. CI will pass even if the output is wrong, unless a human reads the log.

### 📝 Review notes

For C tests, prefer tiny executable tests with assertions and named boundary cases. Add cases for exact-fit buffers, truncation, null input, and allocation failure paths.

### 💡 Takeaway

> **A C test should fail by itself when the code breaks, without asking a reviewer to read terminal output.**
